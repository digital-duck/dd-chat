dd-chat

A Streamlit app: ask one question, and up to five LLMs answer it side by side.

A small, working showcase of GraphLang: the chat logic is a graph file.

https://github.com/digital-duck/dd-chat
dd-chat sends one question to between one and five chatbots and shows their answers in columns. It is also a showcase of GraphLang: each chat turn is a graph file, and the app runs that graph.

Outline

    The outline lists every slide title; click a line to jump.

    The problem: comparing LLM answers

    • Answers from different models are hard to line up when you ask each one in a separate window.
    • The same goes for different prompts sent to the same model.
    • Each question to a billed provider costs money: one question is one call per chatbot.
    • To compare models fairly, you need the same question, the same history and the time and cost of every answer.
    Comparing models by hand is slow, and the answers end up scattered across windows. Cost matters too: with Anthropic or OpenRouter, every question you ask is one billed call for each chatbot.

    The idea: chat logic as a graph

    • One chat turn is a GraphLang graph: src/chat_turn.graph.yaml.
    • The app only draws the conversation and runs that graph once per chatbot per question.
    • Comparing answers is a second graph: src/compare_answers.graph.yaml.

    From the code review

    ✔ chat logic kept apart from the UI
    ✔ the same file runs from graf run
    ✔ "a fair demonstration of GraphLang rather than a Streamlit app with a graph added on"
    The central design choice is that the chat logic is not Python inside the app. It is a graph file, so the app keeps the conversations and runs the graph. A code review of the project noted that this keeps the logic separate from the UI.

    One chat turn as a graph

    add_question → trim → answer → add_reply

    • In: the history and the question, plus the chatbot's language, instructions and formatting rules.
    • The question is appended, and the history is trimmed to the last N turns.
    • Out: the reply and the new history.

    Cost cap

    ✔ the GENERATE node makes one model call
    ✔ MeteredLLM(..., max_calls=1) caps each run at one call
    The graph has four nodes. The three SOLVE nodes do plain data work and the GENERATE node calls the model. Every run is capped at one model call, so a turn can never make extra billed calls.

    The same graph without the app

    # check a graph after editing it
graf validate src/chat_turn.graph.yaml

# run one turn from the shell
graf run src/chat_turn.graph.yaml --llm claude_cli:claude-sonnet-5-5 \
    --param question="What is a graph?" --param history='[]'
    • LLM ids have the form <graflang adapter>:<model>.
    Because the logic is a graph file, you can validate it and run it with the graf command, with no Streamlit involved. That makes it easy to test the graph on its own after you change it.

    Chatbots: 1 to 5 per chat

    • Each chatbot has its own provider, model, turns it sees, language, temperature and instructions.
    • Instructions are a system prompt, so you can compare prompts as well as models.
    • Every question goes to all chatbots in parallel, and each one keeps its own conversation.
    • Each answer appears in its own column as soon as it arrives.

    Easy to line up

    ✔ numbered questions, e.g. [4] what is ...
    ✔ a scrollbar per chatbot
    ✔ adjustable pane height and font size
    A chat has between one and five chatbots, and each is configured on its own. Questions are numbered in every column, which makes it easy to compare the answers to the same question.

    There are seven providers. Ollama runs locally and is free; all the others are billed. The anthropic provider goes through the Claude CLI, so it needs no API key, but it cannot handle images or temperature.

    API keys: where they come from

    • 1. A key typed on the Settings page (kept in memory only, never saved)
    • 2. The shell environment, e.g. OPENAI_API_KEY=sk-... dd-chat
    • 3. .env: first ./.env, then ~/.dd-chat/.env
    • An empty value in .env counts as not set.

    src/env_keys.py

    ✔ no Streamlit code
    ✔ follows python-dotenv's convention: the environment beats .env
    ✔ every source ends up in os.environ, where the adapters read it
    A key is taken from the first source that has it: the Settings page, then the environment, then the .env file. A key typed on Settings is never written to disk.

    Inside a round on the Chats page

    • run_round in src/views/multi_chat.py runs one question across all chatbots.
    • Chatbots that would send identical input are asked only once, and the reply is copied (shared_from), so histories stay aligned.
    • Answers are drawn into each column's pane as the futures complete.
    • Chatbots still running past the timeout are given up.
    • A failure stores a retry_{i} job, so the failed chatbot can be retried alone; the other replies are kept.
    Each chatbot runs in its own thread. If two chatbots would send exactly the same input, the model is asked only once, which saves a call. If one chatbot fails, the others keep their answers and you can retry just that one.

    Kernel reuse in chat_engine.py

    • SOLVE nodes run in a Jupyter kernel that GraphLang starts for each run.
    • chat_engine._kernels() lends long-lived _KeptPools and swaps them into runtime.kernels before execute().
    • This cuts the overhead from about 0.7 s to 0.03 s per run.

    Caveat

    ✔ runtime.kernels is an undocumented GraphLang attribute
    ✔ if it is missing, the code falls back
    ✔ kernel sockets go in tmp/ (from a checkout) or ~/.dd-chat (installed)
    Starting a new kernel for every chatbot and every question was slow; the code review listed it as a weakness. The engine now keeps kernels alive and reuses them. It relies on an internal GraphLang attribute, so it falls back to the normal behaviour if that attribute is missing.

    Comparing and judging answers

    • Per answer: response time, tokens and cost; totals per chat.
    • 📋 copy, 🔊 read aloud, 👍 / 👎, and 🏆 for the best answer to each question.
    • Blind mode hides the model names until you pick the best answer.

    compare_answers.graph.yaml

    A model you choose compares the answers to one question:
    ✔ where they agree
    ✔ where they differ
    ✔ what is doubtful
    ✔ which answer is most complete
    You can judge answers yourself, with blind mode if you want to avoid bias, or have a model compare them. The comparison is a second graph, which shows GraphLang being used for more than one task in the app.

    Other features on the Chats page

    • Retry and redo: retry a failed chatbot alone; ↻ asks a chatbot its latest question again.
    • Batch: upload a list of questions (.txt, .csv, .yaml), and every chatbot answers them all.
    • Presets: save a line-up of chatbots under a name and load it later.
    • Attachments: text files and PDFs go to every chatbot; images go only to providers that can read them.
    • Dead links in answers get ❌; addresses on your own machine or network are never requested.
    These are smaller features that make day-to-day use easier. The link checker connects only to verified public IP addresses and re-checks every redirect, so it never requests private addresses.

    Saving, review and export

    • Saved in SQLite at ~/.dd-chat/multi_chat.db (or $DD_CHAT_HOME).
    • save_session uses an optimistic rev: if another tab wrote first, it forks a new session instead of overwriting.
    • Review page: search, read, reopen, disable or delete chats, and import an export file.
    • A leaderboard shows, per model, 🏆 wins, thumbs, time and cost.

    Export

    ✔ YAML: GraphLang-YYMMDD-HHMMSS.chat.yaml, complete, can be imported again
    ✔ Markdown, organised by question
    Every chat is saved automatically. If you have the same chat open in two tabs, neither tab overwrites the other; the second save becomes a new session. The Review page brings saved chats together and ranks the models.

    The five pages and the code layout

    • src/app.py registers five pages with st.navigation:
    • 💬 Chats, 🔍 Review, 📝 Notes, ⚙️ Settings, ℹ️ About
    • Page files hold the UI; shared logic lives beside app.py.
    ModuleWhat
    chat_engine.pyruns the graphs; tokens, cost, kernel reuse (no Streamlit code)
    chat_db.pySQLite: sessions, messages, comparisons, settings
    chat_models.pyproviders, model lists, saved selection
    chat_export.pyYAML and Markdown export, YAML import
    link_check.pythe dead-link check
    All the code is in src. The engine has no Streamlit code, so it can run in worker threads and in tests. The Notes page holds notes with attached files in the same database, and the About page explains how a question travels through the graph.

    How to try it

    # from PyPI
pip install dd-chat
dd-chat

# or from a checkout
git clone https://github.com/digital-duck/dd-chat.git
cd dd-chat
pip install -r requirements.txt
streamlit run src/app.py
    • Requires Python 3.11 or newer and graflang>=0.2.1.
    • Extra arguments are passed on to Streamlit, e.g. --server.port 8502.
    • From a checkout, run from the repo root so .streamlit/config.toml applies.
    • For free: use a local Ollama model or the graflang mock adapter.
    There are two ways to start: install from PyPI, or clone the repo and run Streamlit. If you do not want to pay for API calls, use Ollama or the mock adapter.

    Tests

    pip install -r requirements-dev.txt
pytest tests

# one test
pytest tests/test_chat_db.py::test_second_tab_does_not_overwrite_first
    • No model is called: the tests use the mock adapter, a fake ask and a temporary database.
    • The deployment plan counts 50 tests, with no model or network calls.
    The tests run offline and cost nothing. They cover the database, the engine, export, the link checker, API keys and the pages.

    What is not done yet

    • An early prototype, built on an early prototype (GraphLang).
    • The Claude CLI's cost is not known, and its token counts are estimates.
    • Single-user and local: SQLite in ~/.dd-chat.
    • Login and a hosted PostgreSQL database are only a draft plan.
    • Open questions: how many users, which PostgreSQL host, and how API keys are kept (per session, or stored encrypted per user).
    This is a prototype. A typed API key goes into the process environment, which is fine for one local user but would leak between users on a hosted server. That is why storing keys is the biggest open question in the deployment plan.
